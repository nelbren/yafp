# OSC 133 configuration

[Documentation index](../README.md#guides)

## Windows (PowerShell)

1. Open Windows Terminal, press `Ctrl+,`, and select **Open JSON file**.

2. In the existing `"profiles"` object, add or merge the following settings
   under `"defaults"`:

   ```jsonc
   "profiles": {
       "defaults": {
           // OSC 133
           "rightClickContextMenu": true,
           "showMarksOnScrollbar": true,
           "useAcrylic": true
       }
   }
   ```

   Do not create a second `"profiles"` object if one already exists.

3. Add the following entries to the existing top-level `"actions"` array:

   ```jsonc
   "actions": [
       {
           // OSC 133
           "command": {
               "action": "scrollToMark",
               "direction": "next"
           },
           "id": "User.scrollToMark.2A0DA8E0"
       },
       {
           "command": {
               "action": "scrollToMark",
               "direction": "previous"
           },
           "id": "User.scrollToMark.D3F0B923"
       }
   ]
   ```

4. Bind the action identifiers to the Windows Terminal shortcuts:

   | Shortcut | Action |
   | --- | --- |
   | `Alt+Up` | Scroll to the previous OSC 133 mark. |
   | `Alt+Down` | Scroll to the next OSC 133 mark. |

   Add these entries to the existing top-level `"keybindings"` array:

   ```jsonc
   "keybindings": [
       {
           "keys": "alt+up",
           "id": "User.scrollToMark.D3F0B923"
       },
       {
           "keys": "alt+down",
           "id": "User.scrollToMark.2A0DA8E0"
       }
   ]
   ```

5. Enable OSC 133 in `yafp-cfg.ps1`:

   ```powershell
   $global:YAFP_OSC133 = 1
   ```

6. Reload YAFP or open a new PowerShell session. Run several commands and use
   the scrollbar marks or the configured actions to move between prompts.

Windows Terminal supports the OSC 133 sequences used to identify prompts,
commands, output, and exit status. Marks are stable starting with Windows
Terminal 1.21. See Microsoft's
[Windows Terminal Shell Integration documentation](https://learn.microsoft.com/en-us/windows/terminal/tutorials/shell-integration).

## Unix (Bash and zsh)

1. Enable OSC 133 in `yafp-cfg.bash` or `yafp-cfg.zsh`:

   ```bash
   YAFP_OSC133=1
   ```

2. Reload YAFP or open a new Bash or zsh session. For Bash:

   ```bash
   source /path/to/yafp/yafp-ps1.bash
   ```

   For zsh:

   ```zsh
   source /path/to/yafp/yafp-ps1.zsh
   ```

   zsh emits command-start markers through `preexec` and completion markers
   through `precmd`, with the previous command's exit status. Empty input
   does not create another command block.

3. Run several commands in a terminal that supports OSC 133. The terminal can
   then identify prompts, commands, command output, and command completion.

4. iTerm2 already provides keyboard shortcuts for navigating OSC 133 marks, so
   you do not need to create equivalent actions:

   | Shortcut | Action |
   | --- | --- |
   | `Cmd+Shift+Up` | Go to the previous OSC 133 mark. |
   | `Cmd+Shift+Down` | Go to the next OSC 133 mark. |

   The same commands are available under **Edit → Marks and Annotations →
   Previous/Next Mark**. See the
   [iTerm2 Shell Integration documentation](https://iterm2.com/3.5/documentation-shell-integration.html).

## Semantic command blocks

Bash, zsh and PowerShell emit OSC 133 markers so compatible terminals
can identify prompts, commands, output and exit codes.

```text
OSC 133 ; A  prompt start
OSC 133 ; B  prompt end / user input start
OSC 133 ; C  command start / output start
OSC 133 ; D  command finished, with exit code
```

This is enabled by default in the shell configuration templates:

```bash
YAFP_OSC133=1
```

```powershell
$global:YAFP_OSC133 = 1
```

Set it to `0` if your terminal does not handle OSC 133 correctly:

```bash
YAFP_OSC133=0
```

```powershell
$global:YAFP_OSC133 = 0
```

YAFP preserves the visible prompt behavior when OSC 133 is disabled. When it is
enabled, OSC markers are wrapped as non-printing prompt sequences, so they should
not appear as visible text or disturb cursor positioning.

### Bash integration details

YAFP emits:

- `OSC 133;A` and `OSC 133;B` inside `PS1`;
- `OSC 133;C` from a Bash `DEBUG` trap when a user command starts;
- `OSC 133;D;<exit_code>` at the beginning of the next `PROMPT_COMMAND`.

Internally, the Bash implementation keeps a lightweight command-block model with
fields for id, command text, exit code, start time, finish time, duration, status,
and approximate history positions. The structure also reserves stdout/stderr
fields for a future terminal-side integration, but Bash alone cannot separate or
capture scrollback output without changing how commands are executed.

### PowerShell integration details

PowerShell follows the Windows Terminal integration model:

- `OSC 133;A` is emitted immediately before the visible prompt;
- `OSC 133;B` is returned immediately after the prompt mark;
- `OSC 133;D;<exit_code>` closes a command with its preserved status;
- `OSC 133;D` without an exit code represents empty input.

PowerShell has no shell-native pre-execution hook equivalent to Bash's `DEBUG`
trap, so YAFP does not replace PSReadLine key handlers merely to emit
`OSC 133;C`. Compatible terminals can use `autoMarkPrompts` with the A, B, and D
markers, following the documented Windows Terminal integration model.

### zsh OSC 133 support and fish

The native zsh implementation uses `precmd`/`preexec` hooks for the same
OSC 133 A/B/C/D lifecycle, preserving the previous command's exit status.
YAFP does not currently implement fish support.

### Current limitations

- YAFP cannot draw selectable visual borders around scrollback blocks because it
  is not the terminal renderer.
- stdout and stderr are not captured separately yet.
- buffer positions are approximate Bash history positions, not terminal cell
  coordinates.
- Advanced actions such as copy command, copy output, or copy whole block belong
  in a terminal UI layer or a future YAFP companion renderer.

### Unicode and command history

Unicode display issues depend on both the terminal and its line editor:
Readline in Bash, ZLE in zsh, and PSReadLine in PowerShell. YAFP's automatic
history redraw mitigation applies only to zsh. A cross-shell review reproduced
the residual-character problem in zsh, but not in the tested Bash and
PSReadLine history transitions, with or without YAFP.

PSReadLine can still misplace the cursor for combined emoji: a history redraw
does not correct the editor's own cell-width calculation. YAFP therefore keeps
the native Bash and PowerShell history bindings. If visual remnants occur,
`Ctrl+L` can request a manual redraw, but may not fix a combined-emoji cursor
offset. See the platform scope and tested versions in
[`docs/ARCHITECTURE.md`](ARCHITECTURE.md#cross-shell-unicode-history-review).
